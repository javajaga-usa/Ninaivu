# Project audit — 26 October 2026

Audited revision: `c59e1f2` (Ninaivu 3.3.0). This is an audit, with no runtime
source changes. Five actionable findings follow: four reproduced behavioral
defects and one documented unsafe subprocess pattern. Address the replica
identity issue first.

## Scope and approach

The repository contains approximately 147,000 lines of Python across the app,
extensions, launchers and tools, and 41,000 lines of application JavaScript.
The Python suite collected 7,332 tests, with eight collection-time skips.

Review covered application assembly and request gates; accounts and sessions;
visibility, dates, private items and public links; upload staging and phone
backup; index storage, backup extraction and repair; replica publication and
receipt; model process isolation; extensions; dependency declarations;
deployment configurations; CI and distribution packaging. This combines broad
test execution with focused source tracing, not a claim that every line or
every hardware/network combination has been manually verified.

## Project structure

| Layer | Main responsibilities | Audit emphasis |
| --- | --- | --- |
| Application and server | `Services`, Flask app faces, listeners, host/proxy trust, accounts | Request gates, session boundaries, shutdown and concurrency |
| API and browser | Gallery, console, sharing, studio and family features | Role/scope checks, public links, upload entry points, frontend regression coverage |
| Storage | SQLite index, visibility queries, state bundles, copies and repair | Privacy predicates, transaction lifecycle, extraction and verified publication |
| Archive and engine | Import, resumable work, worker pools and scanning | Read-only source handling, job state and interruption behavior |
| Media and runtime | Image/video processing, faces, OCR and isolated model hosts | Untrusted inputs, bounded resources, optional model failures |
| Cloud and replica | Encrypted Drive/off-site backup, paired computers, read-only replicas | Secret stripping, checksums, account identity and cross-generation state |
| Delivery | Launchers, portable installers, Docker/systemd, extensions and CI | Dependency contracts, release checks and packaged web assets |

The key architectural strength is that file/index safety and access checks
have shared helpers and extensive regression coverage. The main weakness
exposed here is that some callers still enforce related invariants differently:
session identity across replicas, settings publication, and disk admission for
ordinary uploads versus phone-backup pieces.

## Findings

### A-01 — High: a deleted user's replica session can become a different account's session

**Location:** `ninaivu/replica/receive.py:145–149`.

`carry_sessions()` carries an old session whenever its numeric `user_id` is
present in the new snapshot. It does not verify that this is the same account.
`users.id` is an `INTEGER PRIMARY KEY` whose highest deleted value can be
reused. The primary's deletion routine explicitly handles this reuse for many
other references, but it cannot clear sessions held in the replica's older
database.

**Trigger:** a family member signs in on the replica; the administrator deletes
that newest account on the primary and creates another account before the
next snapshot is applied. If the replacement is an administrator, the old
family token resolves to that administrator on the replica's family app.
No replacement password is needed. This does not establish access to the
separate console, because the original session remains bound to its app face.

**Evidence:** the reproduction creates an owner and family account, snapshots
the database, calls the real `auth.delete_user()` on the new copy, creates a
replacement administrator, and carries the old replica sessions. Calling
`auth.session_user()` with the original family token returns the replacement
administrator.

**Remedy:** bind sessions to a non-reusable account identity and verify that
identity across snapshots. At minimum, reject sessions when immutable account
creation identity differs. Test deletion and recreation between two received
generations, including a replacement with greater privileges.

### A-02 — Medium: credential resets and global sign-out do not revoke replica sessions

**Location:** `ninaivu/replica/receive.py:145–149`; related behavior in
`ninaivu/server/auth.py:1220`.

The same carry operation checks only account existence and session expiry.
Changing a password and ending the primary's sessions provides no revocation
information that the replica checks. Published snapshots intentionally omit
the primary's session rows, so simply comparing those rows is insufficient.

**Trigger:** reset an account's credentials or sign it out everywhere on the
primary, then deliver the resulting snapshot. A session already held on the
replica is copied into that snapshot and remains authenticated. This lasts
beyond delivery of fresh account data; it is not merely normal replication
delay.

**Evidence:** a copy of the old database receives a new password and
`auth.end_all_sessions()`. After `carry_sessions()`, the old replica token
still authenticates against the database containing the new password.

**Remedy:** persist a per-account authentication/revocation generation and bind
each session to it. Increment it on credential reset and global revocation;
carry a session only when both stable identity and generation match. Include
disable/re-enable between publications in regression coverage.

### A-03 — Medium: ordinary uploads can cross the reserved free-space floor

**Location:** `ninaivu/media/upload_review.py:43–60`.

The initial disk-space check subtracts `upload.content_length`. Browser
multipart parts commonly omit their own `Content-Length`, so Werkzeug's
`FileStorage.content_length` is zero even though the file contains bytes.
`upload.save()` then writes the entire file without checking space again.
The multipart request's overall length does not populate that per-file field.

**Trigger:** a family member uploads a file while the state disk is only a
little above `phone_backup.KEEP_FREE_BYTES` (2 GiB). The check succeeds using
zero bytes, and the staged file consumes the reserve. Concurrent uploads can
consume still more space before subsequent checks see the writes. Request
size limits and the pending-upload quota do not enforce this disk reserve.

**Evidence:** the reproduction supplies a normal `FileStorage` containing
4,096 bytes with no per-part length, mocks free space to reserve + 1,024 bytes,
and verifies that staging accepts and writes all 4,096 bytes. Media decoding is
stubbed; no real disk is filled.

**Remedy:** obtain a trustworthy staged-stream size before copying, or copy in
bounded pieces while checking/reserving disk space. Account for concurrent
writers and multipart temporary storage. Keep failure cleanup and test parts
without lengths, multiple files, and parallel uploads.

### A-04 — Medium: settings-only changes can leave the replica on stale settings

**Location:** `ninaivu/replica/publish.py:435–443`;
`ninaivu/api/api_library.py:427–440`.

After the publication interval, `Publisher.due()` checks only the size and
modification times of the index and WAL. The published manifest also carries
family settings, but changes to those settings are not part of this check.

**Trigger:** the existing `/api/settings` endpoint changes a replicated setting
such as `nsfw_filter`. It calls `cfg.save()` without writing an audit/index row.
With an otherwise unchanged index, the publisher reports nothing due, leaving
the replica with its previous setting until an unrelated database write or a
manual publication occurs. Most newer console settings endpoints do write an
audit row, so this finding does not imply that every console setting change
fails to propagate.

**Evidence:** an integration reproduction uses the real authenticated endpoint,
verifies the changed setting and successful response, and then verifies that
the publisher remains not due despite the publication interval having elapsed.
A smaller reproduction separately characterizes the publication predicate.

**Remedy:** include a digest or generation of `family_settings(cfg)` in the
published record and due comparison. Do not rely on incidental database
writes to transport settings. Test an idle index and a settings-only change.

### A-05 — Medium: video workers run Python callbacks between fork and exec

**Location:** `ninaivu/media/video_trial.py:169–179` and
`ninaivu/mugil/display.py:318–327`.

Both launch paths pass a Python `lower()` function as `preexec_fn` to lower
ffmpeg's priority on POSIX. These paths run in background threads in an
already multithreaded server. Python explicitly warns that `preexec_fn` is
unsafe in threaded applications because the child can deadlock before exec.
See the [Python 3.13 subprocess documentation](https://docs.python.org/3.13/library/subprocess.html#popen-constructor).

**Evidence and confidence:** source tracing confirms the unsafe launch pattern.
In the broad remainder run, the real-video trial test failed after a child
segmentation fault inside `subprocess._execute_child`, called from
`VideoTrial._run → run_once → try_one`. The same test passes alone. That observed
failure makes the launch path worth prioritizing, but the precise cause of the
native segfault has not been isolated; it is not proven to be caused solely by
the priority callback.

**Remedy:** remove both Python pre-exec callbacks. Use a suitable external
priority wrapper or adjust the child's priority from the parent after launch.
Keep the existing timeout, output capture and partial-file cleanup. Validate
launches after the application's native libraries and background threads have
been initialized, not only from a fresh isolated test process.

- The initial sandboxed full run aborted at the native macOS window test,
  after progressing through approximately 36% of the suite. Socket-binding
  failures and the isolated watcher/window-opening test pass outside the
  sandbox. The unrestricted full run also aborted in native Tk, at
  `test_desktop_panel.py::test_hiding_the_logs_gives_the_height_back` during

  This points to an interaction in the combined native-GUI run, whose cause

  the combined-run abort before claiming a clean single-process macOS suite.
- The remaining segment completed: **4,533 passed, 85 skipped, 6 deselected,

  `test_video_trial.py::test_a_real_trial_copy_is_smaller_keeps_its_tags_and_leaves_the_original_alone`,
  with the child-process segfault described in A-05. That test passes in an

  36% before its Tk abort. Do not add segment and supplementary counts as if

## Design observations and remaining limits

The inspected code has substantial defensive work: centralized request gates,
hashed session tokens, role/scope/date checks, restrictions on public-network
access, bounded HTTP concurrency, model process isolation, verified backup
manifests, guarded extraction, and checksum-verified file repair. These are
positive source observations, not proof that no other vulnerabilities exist.

The largest maintenance risks are cross-generation identity/state handling and
invariants duplicated across entry points. The first four findings sit at these
boundaries; the fifth concerns native-process launch safety. Prioritize stable
account identity and revocation metadata, a
shared bounded upload writer, explicit replica configuration generations, and
safe subprocess launch from video workers.

Windows/Linux installers, real cloud accounts, phone hardware, a deployed
reverse proxy and every optional AI model were not manually exercised. No live
family library was used for browser automation. This audit does not certify
dependency advisory status or production deployment security.
