# Project audit — 3 November 2026

Audited starting revision: `6527383`. This pass includes runtime fixes and nine
new regression tests, focused on storage relocation and startup coordination.
Broader checks covered repository lint, application JavaScript syntax, installed
Python dependency compatibility, and existing account, authorization, archive,
backup and download tests.

## Findings and fixes

All findings below were addressed in this working tree.

| Finding | Trigger and effect | Improvement |
| --- | --- | --- |
| Destination startup lock released too soon | After publishing a relocated index, a competing start could acquire the destination startup lock before the original process acquired its server lock. Startup work was no longer serialized. | The relocation operation retains the destination startup lock in the caller's startup stack through server-lock acquisition. Startup also reloads configuration under the appropriate locks if the location changed concurrently. |
| Existing observers keep reading the old folder | A Control Panel or restart helper created before a move keeps its old state path. Run records are written in the destination, so the observer cannot find the restarted server. Calling `starting.begin()` a second time does not move an existing heartbeat. | Run-record and startup-progress readers follow relocation notes. The Control Panel refreshes its state path before reading the server record. A dedicated heartbeat handover keeps the original start time, writes progress at the new location, and removes the old note. |
| Original launchers break after two moves and recovery cleanup | With A → B → C, deleting B's recovery `index.db` caused A's resolver to reject B before following its note to C. | Resolve the entire chain before requiring the final index. Canonicalize each destination, detect loops, and validate forwarding records. |
| Malformed move records can interrupt startup | Valid JSON with the wrong shape, such as an array or a numeric destination, raises an uncaught `TypeError`. A non-object copied configuration also interrupts the move without normal failure cleanup. | Validate destination records and configuration objects explicitly. Failed moves retain the original library, remove the incomplete destination, clear the request, and record a useful error. |
| Old runtime records copied with library data | A leftover `ninaivu.run` could appear at the destination before the new server was serving, carrying the old process identity and shutdown token. | Exclude the runtime record and its partial file from copies and verification. The new server publishes its own record when ready. |

Regression tests reproduce the former failures for forwarding chains, stale
observers, heartbeat handover, malformed records/configuration, copied runtime
identity, and startup lock lifetime. Existing tests continue to cover failed
verification, missing destination drives, an active source server, and a
conflicting destination.
